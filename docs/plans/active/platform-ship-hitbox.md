# 제안: 탑다운 배 충돌 크기(엔진)와 그림 크기(렌더)를 한 곳에서 (S5 → S1·S2·S3)

- 2026-10-15 · 배경: 사용자 실기기 지적 "적이 일정 간격에서 멈춰 있다"(1bfe88e로 수정).
  같은 날 배 그림 크기가 세 번 바뀌었다(S3 0.85 → S1 0.74 = 13%). 그때마다 엔진 캡슐(ship_tiers topHalfWidth·topHalfLength)을 사람이 다시 맞췄다(17·40 → 12·30 → 10·26).
- 문제: 같은 배 크기가 두 곳에 산다.
  - 렌더: fx_map `topShip.scale` × 등급별 선체 그림 크기(`td:<tier>:hull` 프레임) — 선체 강화 단계마다 프레임 자체가 커진다.
  - 엔진: ship_tiers `topHalfWidth`·`topHalfLength`(전장 단위 숫자) — 배율도 단계도 모른다.
  - 한쪽만 바뀌면 적이 그림보다 멀리서 멈추거나(지적된 버그) 그림 안으로 파고든다. 지금 테스트는 엔진 값만 읽으므로 **어긋나도 통과**한다.

## 제안 (추천: A + C)
### A. 배율은 한 키, 엔진이 곱한다 (숫자 한 곳)
- ship_tiers의 캡슐 값을 **배율 1 기준 선체 크기**(그림의 선체 반폭·반길이를 전장 단위로)로 바꾼다: `topHullHalfWidth1`·`topHullHalfLength1`.
  - 지금 값 ÷ 0.74 = t1 약 13.5·35 / t2 14.9·39 / t3·t4 17.6·43(S3가 그림에서 재서 확정).
- 배 그리기 배율은 **엔진도 읽는 공용 키 하나**로: `waves.top.shipScale`(지금 fx_map `topShip.scale` 0.74를 옮김). 렌더 `top_scene_painter`는 이 키를 읽는다(S3 한 줄).
- 엔진 캡슐 = 배율 1 크기 × `shipScale`. 배율을 바꾸면 그림과 충돌이 같이 바뀐다 → 사람이 다시 맞출 일이 없다.
- 선체 강화 단계(프레임이 커짐)도 같은 식으로 맞추려면 `topHullGrow`{width 0.03, length 0.05}(단계당, S3 수치)를 두고 엔진이 `battle.shipLook.hull` 단계로 곱한다(선택 — 지금은 4단계 기준 한 값).
- 담당: S2(표 키 이동·검증), S3(렌더가 새 키 읽기 + 배율 1 선체 크기 측정), S5(엔진 연결 + 테스트).

### B. 렌더 그림에서 자동으로 재기 (대안 — 추천 안 함)
- 아틀라스의 선체 그림 불투명 영역을 빌드 때 재서 표를 만든다. 정확하지만 생성 도구가 하나 더 생기고, 돛·포신을 빼는 규칙(적이 돛 밑까지)을 코드로 정해야 해서 복잡하다.

### C. 어긋남을 잡는 테스트 (A와 함께)
1. **렌더 쪽 일치 테스트**(apps/game/test, S3·S5): 각 등급·선체 단계의 선체 그림 불투명 영역(돛·포신 층 제외)을 실제 배율로 재서,
   엔진 캡슐과 반폭·반길이 차이가 **±2 전장 단위** 안인지 본다. 배율·그림·표 중 하나만 바뀌면 실패한다.
2. **엔진 회귀 테스트**(이미 있음, 숫자 대신 표에서 읽음): 20초 동안 적이 캡슐 안으로 들어가지 않고, 10마리 넘게 닿고, 접촉 공격이 난다.
   배 크기를 바꿔도 깨지지 않는다(캡슐을 표에서 읽으므로) — 대신 1번이 '그림과 같은가'를 지킨다.
3. **보이는 거리 테스트**: 프레임 띠 도구(apps/game/test/proto/top_strip_test.dart)로 스테이지 10 시작 선원 20초 — 배 그림 가장자리에서 가장 가까운 적까지 거리(화면 dp)의 중앙값이 **8dp 이하**(적이 배에 붙는다). 사용자가 본 것을 그대로 숫자로 지킨다.

## 순서
1. S3: 배율 1 선체 크기 측정값과 렌더가 읽을 키 위치 합의(`waves.top.shipScale` 추천 — 엔진과 렌더가 모두 이미 waves.top을 읽는다).

3. S5: 엔진 캡슐 = 값 × shipScale, C-1·C-3 테스트.
4. S3: 렌더가 새 키를 읽게 바꾸고 fx_map 키 삭제.
